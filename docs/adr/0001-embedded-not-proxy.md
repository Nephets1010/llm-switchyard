# ADR-0001：为什么是嵌入式网关，而不是 sidecar 或反向代理

- **状态**：已接受
- **日期**：2026-10-09

## 背景

「LLM 网关」在市场上的形态高度一致：一个独立的进程（多为 Python），业务方把 `base-url` 指过去。
代表项目是 LiteLLM、Portkey、Cloudflare AI Gateway。

这是有道理的 —— 网关天然适合旁路部署。但对中国大陆的一批特定客户，这个形态有硬伤。

## 决策

**做嵌入式网关：以 starter 形式嵌入业务 Spring Boot 进程，不要求额外部署代理层。**

## 理由

### 1. 数据不出内网（合规硬约束）

金融、政企、医疗客户的模型调用数据往往含身份证号、病历、账户信息。
走独立网关意味着请求要穿过一个**额外的网络边界** —— 而这道边界在客户的合规审计里需要单独论证、
单独授权、单独部署防火墙策略。数据本来在应用内不出网，加个网关反而多了一道需要解释的路。

### 2. 复用既有的认证与限流体系

sidecar 形态下，网关有自己的认证层。客户已经有一套完整的 Spring Security + 网关限流 +
租户体系，结果 LLM 网关成了体系外的孤岛：租户信息传不进去，审计日志也散在两处。

嵌入式之后，`SwitchyardRouter` 直接读同一个 `SecurityContext`，租户维度天然贯通。

### 3. 私有化部署的现实约束

很多客户的 K8s 集群只允许部署经过安全评审的镜像。一个来路不明的 Python 网关镜像
（哪怕开源）走完评审流程可能要两个月 —— 而嵌入式 starter 只是项目里的一个依赖，
跟着主应用一起过审。**它是主应用的一部分，不是一个新的信任边界。**

### 4. 少一跳网络，少一层排障

嵌入式意味着调用链上没有额外的进程、端口、代理规则。
出问题时「网络在哪一层断的」这个问题不存在。

## 代价（诚实列出）

| 代价 | 是否可接受 | 缓解 |
|---|---|---|
| 每个业务服务都要引入 starter | ✅ | 依赖只有 starter + provider + core，无重量级传递依赖 |
| 多实例需要各自装配 | ✅ | 与业务同生命周期，不需要额外的协调服务 |
| 不能被多个业务团队共享 | ⚠️ 部分 | 这是代价。若需要共享，退回 sidecar 形态 |
| 无法在不重启应用的情况下改配置 | ⚠️ | 价格表已支持热更新；路由变更走配置中心 |

## 与 LiteLLM 的关系（不回避）

**如果你的场景是多云聚合、要接 300 个模型、需要成熟的负载均衡算法，LiteLLM 是更成熟的选择。**

我们打的是另一格：**中国大陆企业的私有化 Java 服务**，需要复用既有认证与限流体系、
数据不能出境、且要按部门精确核算 AI 成本。这两个方案的适用场景不重叠，不必二选一。

## 如何保证「嵌入式」不是一句口号

三条可验证的约束：

1. **`router.route()` 返回标准 `ChatModel`**，业务代码只改 `ChatModel` 的来源，不改任何调用方式；
2. **镜像体积不显著增加** —— provider 层用 JDK 内置 `HttpClient` 而非额外 HTTP 客户端栈；
3. **不需要额外部署任何进程** —— `docker compose up` 里除了 mock-llm（测试后端），没有网关容器。
