# 架构决策记录 · Architecture Decision Records

本目录记录**为什么**这样设计，而不只是「做了什么」。
代码能回答「做了什么」，只有 ADR 能回答「为什么不那样做」。

有异议？**提一份新的 ADR 反提案**，比在 issue 里争论有效得多。

## ADR 模板

```markdown
# ADR-XXXX：<一句话标题>

- **状态**：提议 / 已接受 / 已废弃（被 ADR-YYYY 取代）
- **日期**：YYYY-MM-DD
- **影响范围**：<模块 / 文件数>

## 背景
<促成这个决策的客观事实与约束。避免「我们需要 X」式的表述，写清楚约束是什么。>

## 决策
<我们决定做什么。用陈述句，不留模糊。>

### 支撑理由
1. <理由>
2. <理由>

### 代价（我们明确接受的）
- <代价>，因为 <为什么仍然值得>

## 落地机制
<这个决策如何变成「可机器校验」而非口头约定。这一节是 ADR 与普通设计文档最大的区别。>

## 升级 / 变更条件
<什么情况下这个决策应该被重新审视。>

## 备选方案（被否决）
| 方案 | 否决理由 |
|---|---|
| <方案> | <理由> |
```

---

## 写作原则

1. **写约束，不写偏好。** 「Boot 3.5 已 EOL，用户不能先做框架迁移才能试用」是约束；
   「我们更喜欢 Boot 3.5」是偏好。前者能被别人检验，后者只能被争论。
2. **必须写代价。** 任何决策都有代价，不写就说明还没想清楚。
3. **必须写落地机制。** 决策若无法被机器校验，它迟早会在某次重构中被无声破坏
   （本项目的 jacoco 门禁就曾因中文路径下静默失效，差点变成一个「看起来在生效、实际在放行」的门禁）。
4. **必须写被否决的备选方案。** 后来的人不必重新推导一遍。
